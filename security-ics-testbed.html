PLC / SCADA Security Testbed

A self-built lab that replicates a small industrial process — a soft-PLC, a SCADA/HMI and a simulated field process on a segmented network — so I can safely study how ICS attacks work and, more importantly, how IEC 62443 controls stop them. All offensive testing stays inside the isolated lab.

01 Objective

To understand ICS attacks the only way that really sticks — by carrying them out against a system I control, then defending it. The testbed lets me connect what I already know as a builder (PLC logic, Modbus, HMI) with the attacker's and defender's perspectives, end to end.

02 The Testbed

  • Soft-PLC. OpenPLC running ladder/structured-text logic and exposing a Modbus/TCP server — standing in for a real controller.

  • SCADA / HMI. An HMI polling the PLC and driving a simulated process (tank level, motor, valve) so the impact of an attack is visible.

  • Segmented network. Layout mirroring the Purdue model — field, control and supervisory zones — with a firewall between conduits.

  • Attacker & monitor. An isolated attacker host plus a Wireshark sensor on a SPAN port to observe every step from both sides.

03 Attacks I Study

  • Unauthorized writes. Sending Modbus write commands to flip coils or change setpoints — Modbus has no authentication, so this is the core ICS threat.

  • Replay & MITM. Capturing legitimate commands and replaying them, or sitting between HMI and PLC to alter values in transit.

  • Denial of service. Flooding the controller to disrupt the polling loop and observe availability impact.

  • Weak-auth abuse. Exploiting default credentials and exposed management interfaces on the HMI/engineering side.

04 Hardening (IEC 62443)

For each attack, I apply and validate the control that defeats it:

  • Zones & conduits. Segment the network and enforce firewall rules so only the HMI may talk Modbus to the PLC — no rogue masters.

  • Access control & hardening. Remove default credentials, disable unused services, restrict engineering access, and apply least privilege (FR 1 & FR 2).

  • Monitoring & response. Alert on unauthorized writes and traffic anomalies via the Wireshark/tshark sensor (FR 6).

  • Secure comms where possible. Tunnel or wrap plaintext protocols and demonstrate the availability trade-offs OT teams must weigh (FR 3 & FR 4).
